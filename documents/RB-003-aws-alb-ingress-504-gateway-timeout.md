# RUNBOOK: RB-003 - AWS ALB / Ingress 502 Bad Gateway & 504 Gateway Timeout

- **Runbook ID:** RB-003
- **Severity Level:** Sev-1 (Critical)
- **Service:** API Gateway / AWS Application Load Balancer (ALB) & Ingress Controller
- **Target Systems:** AWS ALB, AWS CloudFront, Nginx/Envoy Ingress Controller, Upstream Services
- **Applicable Environments:** Production
- **Owner:** Network & Edge Operations / CloudOps SRE
- **Last Verified:** 2026-09-05

---

## 1. Overview & Alert Symptoms

Users and client applications are receiving HTTP 502 (Bad Gateway) or HTTP 504 (Gateway Timeout) errors at the edge load balancer. 
- **HTTP 502:** The ALB received an invalid response, connection reset (RST), or TCP close from the backend target before finishing the handshake or response headers.
- **HTTP 504:** The ALB established a connection, but the upstream application failed to return a response within the configured idle timeout period (default 60 seconds).

### Common Alerts:
- `ALB5xxErrorRateSpike`: 5xx errors > 2% of total traffic over 3 consecutive minutes.
- `UnhealthyHostCountExceeded`: Unhealthy hosts in target group > 25%.
- `TargetResponseTimeDegraded`: P95 target response time > 5.0 seconds.

---

## 2. Immediate Triage & Impact Assessment (First 5 Minutes)

1. **Verify CloudWatch Metrics for the Target Group and Load Balancer:**
   ```bash
   aws cloudwatch get-metric-data --metric-data-queries file://alb-queries.json --start-time $(date -u -v-15M +%Y-%m-%dT%H:%M:%SZ) --end-time $(date -u +%Y-%m-%dT%H:%M:%SZ)
   ```
   *Key Metrics to Check:*
   - `HTTPCode_ELB_502_Count` vs `HTTPCode_Target_502_Count` (generated by ALB vs generated by upstream container).
   - `HTTPCode_ELB_504_Count` (generated by ALB due to upstream timeout).
   - `UnhealthyHostCount` (number of failed health check pods/instances).

2. **Check Target Group Health State:**
   ```bash
   aws elbv2 describe-target-health --target-group-arn <target-group-arn> \
     --query 'TargetHealthDescriptions[?TargetHealth.State!=`healthy`].[Target.Id,TargetHealth.State,TargetHealth.Reason,TargetHealth.Description]' \
     --output table
   ```

## 3. Diagnostic Procedures

### Scenario A: HTTP 502 with `Elb.InternalError` or Connection Reset by Peer

1. **Check Keep-Alive Timeout Mismatch:**
   *Root Cause Rule:* The upstream application/container server's keep-alive timeout **must be strictly greater** than the ALB's idle timeout.
   - If ALB Idle Timeout = 60s, upstream container keep-alive timeout MUST be >= 65s.
   - If upstream closes the connection first, the ALB sends a request into a closing socket and returns a 502.
2. **Inspect Upstream Ingress Controller (Nginx / Envoy) logs:**
   ```bash
   kubectl logs -n ingress-nginx -l app.kubernetes.io/name=ingress-nginx --tail=200 | grep -E ' 502 | 504 '
   ```

### Scenario B: HTTP 504 with Slow Target Response Time

1. **Check if upstream pods are thread-locked, CPU throttled, or blocking on downstream I/O:**
   ```bash
   kubectl top pods -n production -l app=api-service
   ```
2. **Review ingress access logs for specific high-duration endpoints:**
   ```bash
   kubectl logs -n ingress-nginx -l app.kubernetes.io/name=ingress-nginx --tail=500 | awk '$9 ~ /504/ {print $7}' | sort | uniq -c | sort -nr
   ```

## 4. Immediate Mitigation & Remediation Steps

### Action 1: Temporary ALB Idle Timeout Increase (If Workloads are Long-Running)
If a legitimate batch processing workload or slow query is exceeding the 60s timeout:
```bash
aws elbv2 modify-load-balancer-attributes \
  --load-balancer-arn <alb-arn> \
  --attributes Key=idle_timeout.timeout_seconds,Value=120
```

### Action 2: Scale Up Backend Service Replicas
If backend targets are overwhelmed by concurrency spikes:
```bash
# Temporarily double the replica count
kubectl scale deployment/api-service -n production --replicas=20
```

### Action 3: Drain & Restart Unhealthy Targets
If target instances or pods are in an unrecoverable hung state:
```bash
kubectl rollout restart deployment/api-service -n production
```

### Action 4: Enable Edge Rate Limiting / WAF Shield
If traffic analysis reveals a volumetric DDoS or scraping bot attacking an unoptimized endpoint:
```bash
# Associate rate-limiting rule to AWS WAF WebACL
aws wafv2 update-web-acl --scope REGIONAL ...
```

## 5. Verification & Health Check

1. Confirm `UnhealthyHostCount` drops to `0`:
   ```bash
   aws elbv2 describe-target-health --target-group-arn <target-group-arn> \
     --query 'TargetHealthDescriptions[].TargetHealth.State' --output text
   ```
2. Monitor HTTP 200 vs 5xx error ratios in ALB CloudWatch metrics:
   Ensure 5xx error rate returns to < 0.05%.
